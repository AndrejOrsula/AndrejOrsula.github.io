How this site runs Rust in the browser: an egui calculator, gymnasium_rs, training with Oniro and a 3D viewer for SimForge.

This site is a static Zola build with no server, yet several of its pages run real programs in your browser. Most are Rust compiled to WebAssembly (WASM). This post shows the live demos and the small amount of code that connects them to the pages.

The simplest is the calculator below: a Rust application with an egui interface. Press Load demo, then try 7 + 5 =.

The demos on this site

  • Calculator: the egui application above, 1.2 MB of WASM.
  • gymnasium_rs: reinforcement-learning environments in Rust, 0.2 MB of WASM.
  • Oniro: reinforcement-learning training with Burn, 3.0 MB of WASM.
  • SimForge explorer: a WebGL 2 viewer without WASM that loads one 0.1–0.6 MB model at a time.

WASM sizes are compressed downloads, measured in October 2026.

Building a demo with egui and Trunk

Each embedded demo is a Cargo crate in the demos/ directory of the site repository; the calculator is demos/calc. It builds as a cdylib and depends on eframe, egui’s application framework, with only its glow backend, which draws through WebGL in the browser:

[lib]
crate-type = ["cdylib"]

[dependencies]
eframe = { version = "0.36", default-features = false, features = ["glow"] }
egui = { version = "0.36", default-features = false }

Trunk builds the crate from an ordinary index.html. A single <link data-trunk rel="rust"> tells it to compile the crate, generate the JavaScript glue with wasm-bindgen and shrink the module with wasm-opt. The rest of the page is the canvas that egui draws on and an element for startup errors:

<link data-trunk rel="rust" href="Cargo.toml" data-wasm-opt="s" />

<canvas id="egui_canvas" role="application" aria-label="Calculator"></canvas>
<div id="egui_error" role="alert" hidden>Loading calculator…</div>

On the Rust side, #[wasm_bindgen(start)] runs as soon as the module loads and starts eframe’s web runner on that canvas. A startup failure becomes a readable message in egui_error instead of a silent panic:

#[cfg(target_arch = "wasm32")]
#[wasm_bindgen(start)]
fn main() {
    wasm_bindgen_futures::spawn_local(async {
        // Find #egui_canvas; report a missing canvas with show_startup_error.
        if let Err(error) = eframe::WebRunner::new()
            .start(
                canvas,
                eframe::WebOptions::default(),
                Box::new(|cc| Ok(Box::new(CalculatorApp::new(cc)))),
            )
            .await
        {
            show_startup_error(&format!("Calculator failed to start graphics: {error:?}"));
        }
    });
}

The application itself is plain egui. Its ui method sizes the display and the keypad to the available space in every frame, so the calculator fills any frame the page gives it. The arithmetic lives in a separate model module without egui, so its tests run natively with cargo test.

Building with the site

Before Zola runs, build_demos.sh builds every crate in demos/ with the pinned Trunk version:

trunk build index.html --release --locked \
    --public-url "/demos/$demo_name/" --dist "$destination" --filehash=false

The output goes to static/demos/<name>/, which Zola copies unchanged. The script builds into a fresh directory and replaces the old output only once every required demo has a non-empty JavaScript and WASM file, so a failed build never ships a half-updated demo. It also strips local build paths, which Rust embeds in panic messages, from the WASM.

Embedding with a shortcode

A page embeds a demo with one shortcode call:

{{ wasm_demo(id="calc", title="Calculator built with egui", ratio="2 / 3", max_width="64%", poster="img/demos/calc-preview-light.webp", poster_dark="img/demos/calc-preview-dark.webp") }}

The wasm_demo shortcode renders an <iframe> that starts on about:blank, with the demo’s URL kept in data-src, and a Load demo button over it. Behind the button is a poster: a screenshot of the demo in a light and a dark variant, because the calculator follows your system’s color scheme. Until you press the button, the page downloads nothing from the demo. A small script, wasmDemo.js, then:

  • checks the URL with a HEAD request first, so a missing build shows an error and a Try again button instead of an error page inside the frame;
  • loads the demo in the frame and shows it once its document has loaded;
  • reports progress and errors in a status line that screen readers announce.

The iframe isolates the demo from the page: egui owns its canvas, keyboard and pointer input, and the site’s styles cannot leak into it. The ratio and max_width arguments set the frame’s shape, and egui adapts its layout to it.

Larger project demos register a route in the site configuration instead. Their frame counts as ready only when the demo posts a wasm-demo-ready message from the expected origin, with the right demo id and a build identifier. A demo that stays silent for 20 seconds gets an error and a link to its full-page version. A route marked as unavailable renders a poster and a short note instead, as on the pyo3_bindgen page today.

Full-page demos

Some demos are applications in their own right and need the whole window. gymnasium_rs and Oniro are built in their own repository and published as a separate site under /gymnasium_rs/; this site links to them with a preview.

The gymnasium_rs demo runs six classic-control environments, each with a small hand-written controller. Its swarm lab simulates up to 16,384 copies of one environment, each with its own randomized physics. Oniro, a Rust reinforcement-learning trainer built on Burn, trains a PPO agent on 16 CartPoles and offers a WebGPU tier for browsers with a real GPU. All of the simulation and training runs on your machine.

When WASM is not the answer

SimForge generates its assets with Blender, which cannot run in a browser, so its page ships the results instead: GLB models that SimForge exported, and about 750 lines of plain JavaScript that render them with WebGL 2. It uses the same click-to-load pattern: until you open the viewer, the page shows a poster and loads no model.

Testing in three browsers

Each change to the site runs its browser tests in Chromium, Firefox and WebKit with Playwright. For this post, a test presses Load demo from the keyboard, waits for the calculator’s canvas, clicks 7 + 5 = on it and checks that the canvas changes. Another test makes the demo URL fail with HTTP 503 and checks that the page shows an error. Unit tests of wasmDemo.js cover the Try again button.
